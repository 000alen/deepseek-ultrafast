# Hackathon serving on B300

Start with **Inkling 2 Mini and Ornith-1.5-122B NVFP4, each at one replica per B300**. Inkling has published concurrency data and Ornith is the stronger compact coding candidate to qualify. Use **DeepSeek-V4.1-Flash-1017 on a continuously batched runtime** as the quality baseline and fallback. If difficult tasks dominate, test MiniMax-M3.1-Flash alongside it.

## Capacity model

Assume 500 enrolled users. Let `A` be the number actively producing requests, `T` the interval in seconds between requests for each active user, `I` mean prompt tokens, `H` the **token-weighted** reusable prefix fraction, and `O` mean generated tokens including reasoning and tool arguments. The effective rates are `R = A/T`, `prefill = R × I × (1 − H)` and `decode = R × O`. The per-GPU columns apply a planning utilization of 65% and assume evenly loaded independent TP1 replicas. Round targets up when selecting a test rate. Replay prefill and decode together to validate the latency targets.

| Scenario | Users / interval | Prompt / reused / output | Requests/s | Node demand input / output tok/s | 8 GPUs, per GPU input / output | 16 GPUs, per GPU input / output |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| Light | 50 / 90 s | 8,000 / 50% / 1,000 | 0.56 | 2,222 / 556 | 428 / 107 | 214 / 54 |
| Base | 125 / 60 s | 16,000 / 50% / 1,536 | 2.08 | 16,667 / 3,200 | 3,206 / 616 | 1,603 / 308 |
| Heavy | 250 / 45 s | 32,000 / 60% / 2,048 | 5.56 | 71,111 / 11,378 | 13,676 / 2,189 | 6,838 / 1,095 |
| Cold kickoff | 500 over 30 s | 8,000 / 0% / 1,024 | 16.67 | 133,333 / 17,067 | 25,642 / 3,283 | 12,821 / 1,642 |

If every active agent in the base case calls every 15 s, demand becomes 8.33 req/s, 66,667 uncached input tok/s and 12,800 output tok/s. Halving usable cache hits from 50% to 25% raises base prefill demand from 16,667 to 25,000 tok/s. Doubling generated tokens to 3,072 doubles decode demand to 6,400 tok/s. At 80 tok/s per stream, a 1,536-token answer takes 19.2 s after generation starts. With 2 s until generation starts, Little's law gives about 44 requests in flight at base load, about 5.5 per worker on one node.

At 24 total hours of base activity, the event generates about 180,000 requests, 1.44B uncached input tokens and 276.5M output tokens. Sustaining the same load across all 48 hours doubles those totals. Provisioning follows peak throughput and latency even when activity hours are shorter than the reservation.

A literal simultaneous cold start at the table's per-request sizes injects 4 million prompt and 512,000 output tokens. Giving 95% of those requests a first token in 5 s would require about 760,000 uncached prompt tok/s before scheduler and decode overhead. If all 500 streams must advance at 50 tok/s, decode alone demands 25,000 output tok/s. Treat synchronized kickoff as its own acceptance test. Shape arrival rates or reserve further capacity if it matters to the event.

### Baseline and hardware limits

- Hugging Face measured Inkling with DSpark at **148 output tok/s at concurrency 1**, **1,621 at concurrency 16** and **4,059 at concurrency 64** on one B300, using 1,024 input and 1,024 generated tokens. Plain decode delivered 1,320 output tok/s at concurrency 64. Eight replicas at the 64-stream DSpark point would yield about **32,470 output tok/s** and 512 outstanding requests, assuming linear scaling on that same workload. At 65% planning utilization that is about **21,106 output tok/s**. Because input and output lengths match, that benchmark concurrently processes roughly the same input-token rate. The shorter context and closed-loop request pattern leave cold kickoff prefill and p95 user latency unqualified. [Reproduction and measured figure](https://huggingface.co/blog/inkling2mini#speculative-decoding)
- The native worker consumes the complete request on every rank before it starts the next. Substituting the README's best-case TP8 rates into the base workload gives `8,000 / 85,000 + 1,536 / 2,060 = 0.840 s/request`, or **1.19 requests/s** saturated and **0.77 requests/s** at 65% planning utilization. Two TP8 replicas give **2.38** saturated and **1.55** at 65%. Two TP4 replicas per node at the *GB300* README rates give a **2.02** saturated / **1.32** planned proxy per node. Different prompts, acceptance length, cache traffic and B300 TP4 measurements can move these rates. [Native worker](../crates/server/src/engine.rs#L207), [README benchmarks](../README.md#performance)
- With 288 GB nameplate per B300, one node has 2,304 GB physical HBM. Use the actual allocatable memory reported by CUDA. An Ornith TP1 example using 90% of 288 GB, 77.63 GB of NVFP4 file bytes as a resident-weight proxy, and a separate 30 GB allowance inside that limit leaves 151.6 GB for sequence and prefix state. With 132.95 GB FP8, it leaves 96.3 GB. [NVIDIA B300 specifications](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory/latest/components.html), [Ornith config](https://huggingface.co/ornith-ai/Ornith-1.5-122B-NVFP4/blob/f049036f794622db10bb69855bf9819207334626/config.json)
- Ornith uses 12 GQA layers with 2 KV heads of width 256 and 36 Gated DeltaNet layers. BF16 K and V use `2 × 12 × 2 × 256 × 2 = 24,576 bytes/token` and the FP32 GDN matrix state is `36 × 64 × 128 × 128 × 4 = 151 MB` per sequence per state slot, plus convolution state. At a full 65,536 tokens that is about 1.61 GB KV plus 0.15 GB per sequence for one state slot, or about **56.5 GB for 32 sequences**. With three state slots it is about **66.2 GB** before cache paging, graph buffers and prefix retention. Confirm the runtime's pool, state dtype, cache hit ratio and peak HBM. FP8 KV approximately halves the GQA term and warrants a quality check.
- Inkling makes 8 global and 40 sliding-window layer visits per token. The ideal BF16 target KV footprint is `4,096 × (8L + 40 × min(L, 1,024))` bytes at live sequence length `L`. It is **416 MiB at 8,192 tokens** and **1,184 MiB at 32,768 tokens**, per sequence, before draft KV, convolution state and runtime overhead. At 63 live sequences per GPU, that is 25.6 or 72.8 GiB. Theoretical reads of that full state take about 3.55 or 10.09 ms at 7.75 TB/s; speculative verification and reuse change the actual traffic per generated token. [Inkling architecture and B300 recipe](https://huggingface.co/blog/inkling2mini)
- B300 HBM bandwidth is about 8 TB/s per GPU, about 62 TB/s across HGX. Weight-read cost depends on which experts a batch touches, shared weights, precision, residency and reuse. With uniform independent 8-of-256 routing the expected expert union per layer is `256 × [1 − (1 − 8/256)^batch]`, about 8, 102 and 163 at batches 1, 16 and 32. A 16K BF16 history alone is about 0.40 GB of K/V per sequence before reuse, or about 12.9 GB of reads for a batch of 32 if each KV byte is read once. These are traffic models. Kernel launches, attention, collective latency, achieved bandwidth and speculation determine real throughput. [NVIDIA Blackwell Ultra datasheet](https://resources.nvidia.com/en-us-blackwell-architecture/blackwell-ultra-datasheet), [Ornith config](https://huggingface.co/ornith-ai/Ornith-1.5-122B-NVFP4/blob/f049036f794622db10bb69855bf9819207334626/config.json)
- At Nebius's published $9.50/GPU-hour, running 48 hours costs **384 GPU-hours and $3,648** on one node or **768 GPU-hours and $7,296** on two. With 6 additional hours of qualification on each node, totals are **$4,104** and **$8,208**. Storage, networking and taxes are extra. A provider quote and an actual reservation determine price and availability. [Nebius pricing](https://nebius.com/prices)

## Serving adaptation

The Inkling launcher uses the public single-card benchmark settings and adds the model-specific reasoning and tool parsers. Run it in the [Inkling-specific SGLang build](https://docs.sglang.io/cookbook/autoregressive/ThinkingMachines/Inkling-2-Mini). The `plain` mode disables speculation for comparison. The NVIDIA multi-architecture release image resolves to `lmsysorg/sglang@sha256:efac853b46811ccb760545b7b29e7119bdf907537ccf6e863fac3011fe8b98de`.

```sh
deploy/serve-inkling.sh --dry-run dspark
CUDA_VISIBLE_DEVICES=0 PORT=8100 deploy/serve-inkling.sh dspark
curl -fsS http://127.0.0.1:8100/health_generate
```

The Ornith launcher uses [vLLM 0.34.0](https://github.com/vllm-project/vllm/releases/tag/v0.34.0) with the exact checkpoint revision, its Qwen-family template and tool parser, prefix caching, chunked prefill and bounded in-flight requests. Each launch starts one replica and exposes the OpenAI API. vLLM also exposes `/v1/messages` and `/v1/responses`. Test the exact agent clients and endpoints before using them. [Ornith serving recipe](https://huggingface.co/ornith-ai/Ornith-1.5-122B-NVFP4#quickstart), [vLLM online serving](https://docs.vllm.ai/en/latest/serving/online_serving/)

On a CUDA Linux B300 host with vLLM installed, pre-stage the pinned revision to the shared Hugging Face cache. Start a pilot worker first.

```sh
deploy/serve-ornith.sh --dry-run nvfp4
CUDA_VISIBLE_DEVICES=0 PORT=8100 deploy/serve-ornith.sh nvfp4
curl -fsS http://127.0.0.1:8100/health
```

Run one process per GPU under the node supervisor with `CUDA_VISIBLE_DEVICES=0..7` and ports `8100..8107`. Give each node its own independent workers. Route from the event's authenticated ingress, using session affinity with load-aware spillover and health checks. Keep a fallback deployment independently routable and pin a session's model and precision. Use a per-key concurrency limit and a queue deadline at ingress. The Ornith vLLM worker's admission limit returns HTTP 503 when its in-flight count reaches 40. Start text traces at a 2,048–4,096-token output budget and use a measured higher limit for long tasks. For Ornith, sweep 32K/64K contexts, TP1 vs TP2, NVFP4 vs FP8 and MTP off vs on with 1–3 drafted tokens. For Inkling, measure DSpark and plain decode at mixed loads and prefer the one with better latency at that load.

For batched DeepSeek, use the checkpoint's [serving integration](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017) and replay the same workload. For MiniMax, follow the [official TP4 recipe](https://recipes.vllm.ai/MiniMaxAI/MiniMax-M3.1-Flash) and verify benchmarks report generated tokens rather than mixed token throughput. Test the best one-node configuration through the event ingress to see whether the second node is needed for capacity. It can also cover a whole-node failure if the remaining node alone passes the required workload.

## Qualification

Prepare a private, sanitized JSONL trace with one Chat Completions body per line. Keep representative tool schemas, request budgets, and consecutive turns with shared prefixes. Set `_session_id` on records where the gateway expects `X-Session-ID`. Sample cold and warm traffic explicitly. The runner sends recorded requests on a fixed-rate or burst schedule and reports end-to-end and first usable output latency, completion rate, token usage and overloads.

```sh
python3 tools/hackathon_load.py --base-url http://127.0.0.1:8100 \
  --model Ornith-1.5-122B --input traffic.jsonl --requests 60 \
  --rate 0.27 --concurrency 64 --timeout 120
```

Use the same trace and total rates at the ingress, including a cold kickoff replay. Use the sample counts and finish reasons to distinguish complete streams, budget truncation and requests with usable content or a tool call. A starting gate for the assumed base workload is 99% successful completion, p95 first usable output at most 3 s and p95 TPOT at most 20 ms. If thinking-heavy tasks exceed this first-output target, qualify their latency with a separate budget. Compare verified task completion and median/p95 time to successful solution over 100 representative coding tasks with identical tools and budgets. A provisional quality gate is within five percentage points of DeepSeek's task completion rate, with paired uncertainty reported. Report failures, truncation, retries and reasoning token usage. Repeat with a worker removed and under sustained load. Use the replay to set the actual launch profile and reservation.

For an internal native-engine comparison of original DeepSeek and 1017, use separate Redis instances. The current fingerprint includes config and tokenizer but omits checkpoint revision. Both releases have identical config and tokenizer blobs and differ in all 48 shared safetensor shards. [Peer fingerprint](../crates/server/src/peer.rs#L20), [Original manifest](https://huggingface.co/api/models/deepseek-ai/DeepSeek-V4.1-Flash?blobs=true), [1017 manifest](https://huggingface.co/api/models/deepseek-ai/DeepSeek-V4.1-Flash-1017?blobs=true)

## Native engine work

The checked-in launchers are serving integrations. Get Baseten authorization for external attendee access to the native engine or a hosted derivative if the proposed setup exposes a substantial set of the engine's features. The standalone model runtimes execute their own code. [Repository license](../LICENSE#L18)

A native Ornith executor needs new model code. Start with the FP8 checkpoint on TP1 and use the vLLM implementation as the reference for checkpoint mapping, logits, recurrent state, tokenizer, tool calls and prefill/decode equivalence. Reuse the CUDA driver, weight staging primitives, GEMM and MoE building blocks where the shapes and formats match, and the server's logging and streaming plumbing.

Implement Gated DeltaNet state updates and chunked prefill, paged GQA, Qwen-family RoPE and the Ornith weight loader. Replace the single `Job` execution lane with a scheduler that interleaves bounded prefill and batched decode, keeps KV pages and recurrent state per request, and frees them on completion or cancellation. Add CUDA graph batch buckets, then MTP verification with correct partial acceptance and rollback of recurrent state. Qualify NVFP4 next. The DeepSeek CED prefill shortcut, DSpark verifier graph and compressed KV snapshot payload are tied to that architecture. Defer RDMA to a separate measured change after defining a new cache format and compatibility key. [Native rank](../crates/engine/src/model.rs#L494), [Native prefill](../crates/engine/src/model.rs#L2279), [Protocol adapter](../crates/server/src/chat.rs), [KV serialization](../crates/engine/src/kvstore.rs)

If Inkling wins the event benchmark, its native port needs the checkpoint's three-pass layer order and loop controllers, per-visit KV, sliding-window and full-attention kernels, mixed NVFP4/MXFP8 weights, and its bundled DSpark draft's inputs and commit rules. First establish target-only logits and cache parity against SGLang. Compare the native batch scheduler against SGLang on accepted work under the same tail latency limits before using it at the event. [SGLang architecture notes](https://docs.sglang.io/cookbook/autoregressive/ThinkingMachines/Inkling-2-Mini)
