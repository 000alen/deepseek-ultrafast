# Continuous batching for DeepSeek Ultrafast

## Scope

Serve **500 concurrent coding-agent sessions** on a fleet of DeepSeek-V4.1-Flash replicas. Qualify **500 simultaneous generating requests** separately as the full-density target. Within a replica, requests join and leave at inference step boundaries, new prompts make progress beside running decoders, and multiple decoders share a target-model forward. Start with the existing Blackwell TP4 and TP8 profiles, DSpark, and local and remote session reuse. Keep the first packed implementation opt-in with `--max-num-seqs > 1`. Qualify up to 1M context on a separate capacity allocation so rare large requests have a defined path.

Use a running set, a per-step token budget, decode priority, and chunked prefill as in vLLM V1. vLLM's recipe for this checkpoint also uses a separate active-sequence cap and a prefill scheduling interval. DeepSeek Ultrafast can run encoder prefill, bounded decoder replay, and packed decode as separate GPU launches under one scheduler plan. This lets each phase use its own kernels and puts the first performance milestone on packed decode. [vLLM architecture](https://docs.vllm.ai/en/latest/design/arch_overview/#scheduler) · [Chunked prefill](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill) · [DeepSeek-V4.1-Flash recipe](https://github.com/vllm-project/vllm/blob/main/recipes/models/deepseek-ai/DeepSeek-V4.1-Flash.yaml)

## Current implementation

Packed serving supports up to 128 resident slots, 128 target rows per launch, and a
configured 1,048,576-token context. The actual launch width depends on rank scratch,
draft width, and admission. Wide autoregressive and DSpark steps use row-addressed cache
state and grouped model work. Scheduling limits active decoders independently from
residency and launch width, budgets prefill beside decode, and guarantees prefills progress.
Each request owns its image staging, sampling state, KV pages, and snapshot cursor.
Sliding-window KV and compressor histories use bounded retained rings. Hot prefixes can
keep an idle slot's pages across turns. Restores and completion exports use bounded copy
quanta on separate streams with fenced ownership and completion events.

The gateway routes using reported prefill, decode, and restore backlog, KV headroom, and
session affinity. Two-node overlays cover four standard TP4 replicas, a three-standard
plus long-context variant, and vLLM expert-parallel comparisons. Host checks cover allocator
arithmetic, slot isolation, scheduler phases, routing, and HTTP behavior. Blackwell parity,
live Redis and RDMA behavior, and 500-user throughput remain deployment qualification gates.

## Coding workload and service targets

Build a frozen workload manifest from representative coding-agent traces. Preserve complete turns, prompt growth, cached and new input, output and requested caps, file and tool-result sizes, thinking mode, concurrent child agents, cancellations, burst correlations, and time spent in tools and between turns. Capture actual harness session headers so independent branches get independent cache identities. Use approved internal traces where available and pin a public InferenceX AgentX replay as the external comparison. Use equal turn inputs, tool timing, cache policy, checkpoint, and output limits across backends. Include warm steady traffic, a cold start at 500 sessions, and production-default output caps as a separate measured cohort. [AgentX standalone benchmark](https://github.com/SemiAnalysisAI/InferenceX/blob/main/inferencex-e2e/docs/agentx-standalone.md)

| Measure | Proposed qualification target for standard coding traffic |
| --- | --- |
| Live workload | 500 independent closed-loop sessions with real tool and think gaps, for a 2-hour peak soak after warmup. |
| Full-density workload | Sustain 500 simultaneous generating streams for at least 10 minutes after ramp. Replenish with staggered requests and measure the population with first output already emitted and continuing token progress. Treat queued, prefill-only, and tool-waiting sessions separately. |
| Time to first token | p95 ≤ 2 s on warm turns with ≤ 8K new input tokens. p95 ≤ 5 s on cold turns with ≤ 32K input tokens. Include gateway queueing and cache transfer. Record larger prompt classes separately. |
| Streaming | p10 per-request useful decode rate ≥ 100 output tokens/s for turns that generate at least 128 tokens. p99 inter-chunk gap ≤ 250 ms across token-bearing chunks, with per-request tail gaps also reported. Include reasoning and tool tokens and exclude SSE metadata and keepalives. |
| Reliability | ≥ 99.5% successful eligible, non-user-cancelled turns at target load. Count server-side rejection, timeout, and stream loss as failures. Report offered traffic, successful completions, and requests meeting all latency and rate targets together. |

These are proposed operating targets. Lock the manifest and targets before comparing engines. Use an open-loop sweep to 1.5× the observed peak arrival rate to find the saturation knee. At the target load, require stable queue depth and no sustained growth in HBM, host memory, or transfer backlog. Beyond saturation, measure refusals, queue deadlines, and recovery time.

## Fleet and capacity model

Start with replicated TP4 groups behind one streaming gateway. Compare one TP8 with two TP4 replicas at equal GPU count where the hardware supports both. Place the standard and long-context allocations on separate capacity so a near-1M prefill can run without freezing normal admission. The standard coding contract starts at up to 128K total context with an explicit output cap up to 8,192 tokens. Route turns exceeding either limit, including larger general API defaults, to capacity configured to honor them. The serving tokenizer and prompt renderer make the final eligibility check before streaming and before applying a narrower context limit. Preserve the existing general API output semantics. Confirm which tier the actual harness uses and measure the resulting tier mix before claiming capacity. [Existing output defaults](SERVER.md#endpoints) · [Current deployment example](../deploy/kubernetes.yaml#L29)

Let `λ` be peak eligible turns/s from the workload, `O` its mean useful output tokens/turn, and `U` its mean uncached input tokens/turn. Provision for `λ × O` output tokens/s and `λ × U` uncached input tokens/s, alongside context-dependent attention, replay, remote KV bytes/s, and snapshot staging. Measure active decoders under load. At a stable operating point their mean is `λ × mean decode duration`. Measure peak occupancy and correlated arrival bursts directly. As a load-generator example, 500 active streams at 100 tokens/s imply 50,000 useful output tokens/s at that rate. With synthetic means of 1,024 output tokens and 8,192 uncached input tokens per turn, that is about 49 turns/s and 400,000 uncached input tokens/s. Use trace-derived inputs for procurement or rollout sizing.

For each pool and topology, measure `λ_safe` turns/s and `D_safe` simultaneous generating streams at the same sustainable operating point on the target mix. Set an initial operating fraction `h = 0.75`. Size homogeneous groups with `ceil(max(λ_peak / λ_safe, D_peak / D_safe) / h) + F`, where `F` is the largest replica count lost in one required failure domain. Use `F = 1` only when placement makes one replica the failure unit. The calculated count assumes linear scaling. Confirm it with actual routing, queue tails after a loss, Redis and fabric saturation, and mixed-load prefill and decode sharing before a production claim. Count warm resident conversations separately through snapshot bytes, Redis state, and transport rates.

For scale intuition, eight GPU-resident requests per replica gives an absolute lower bound of 63 replicas for 500 simultaneous decoders before allowing for prefills, retirement, and failures. At the proposed headroom, even eight **qualified generating** streams per replica would need 85 groups with one spare. Treat eight as an engine canary. Tune wider packing and run an upstream backend in parallel as a capacity baseline.

## Scheduler and request lifecycle

Rank 0 owns the request table, admission and cache reservations, cancellation, and output delivery. Put scheduling policy in a CPU-testable server module and keep CUDA execution in the engine. Publish one immutable `StepPlan` to all TP ranks. Every rank executes the same ordered operations, packed row layout, collective shapes, and graph selection. Results carry the plan ID and a `(slot, generation)` handle. Apply each result once, and reject late results for a recycled slot. A rank failure takes the replica out of service and fails its pending work.

The lifecycle is `Queued → Preparing → Ready → Restoring/Prefilling → Decoding → Retiring → Released`. Restore is optional. A request that finishes after the first sample goes straight to retirement. Wait for input only when there is no runnable work. Arrival, preparation, cancellation, and copy completion wake the scheduler. While serving, incorporate new ready work at the next step boundary without waiting to fill a batch.

Build each plan in this order.

1. Apply completed work and cancellations. Stop issuing new model work for terminal requests and keep their slots reserved until GPU reads, writes, and capture copies are safe.
2. Admit ready requests with tenant credits, a free slot, and a KV reservation. Skip entries waiting on peer I/O or a same-branch predecessor. Within each pool, allow bounded bypass for requests that fit and age large reservations until they receive capacity. In the long-context pool, drain younger admissions when required to fit the oldest aged request. Keep capacity for new prefills and retirement under sustained decode load.
3. Schedule decode by oldest service time, rotating when eligible decoders exceed one packed launch or the plan's time budget. Count one target row for autoregressive decode and the anchor plus reserved verification rows for DSpark. Estimate the worst wait across the remaining launches at admission and cap eligible active decoders to a measured level that meets the streaming SLO. Apply the same launch order and shapes on all ranks.
4. Spend remaining target rows on prefill and replay with a maximum prefilling interval in wall-clock time. Rotate partial prefills. Bound busy prefill by rows and estimated GPU time using measured context and chunk costs. Start kernel experiments at 256 busy rows and sweep cadence at each occupancy. Allow a larger idle quantum up to the existing `--chunk` and the plan budget. Give restore, vision staging, and retirement their own bounded copy or GPU-time budget. Tune the interval against the TTFT and stream-gap SLOs.

| Setting | Contract |
| --- | --- |
| `--max-num-seqs` | Maximum GPU residents, including partial prefill, restore, and retirement. Default `1` selects the incumbent engine. Eight is the initial canary, with production sized from measured page capacity and load. |
| `--max-num-decode-seqs` | Maximum sequences per packed decode launch. Set independently of residency and tune the separate cap on active decoding requests from the stream-gap budget. |
| `--max-num-active-seqs` | Maximum requests simultaneously in the decode phase. Optional rate and gap targets restrict new decoders using observed step costs. |
| `--max-num-batched-tokens` | Cap on live target-model query rows across a plan, including chunk, replay, and verification rows. Start at 8,192 for the canary. Validate at least one maximum configured packed launch and a full 128-row replay can fit. Bound graph-padded rows and draft-model work independently. |
| `--kv-cache-memory-bytes` | Explicit KV pool limit per rank in batching mode. Compute admission against the least capacity across ranks after sizing weights, runtime scratch, communication, graphs, and staging. Fail startup if the configuration cannot serve one maximum-length request. |
| `--hot-kv-cache-memory-bytes` | Maximum bytes within the KV pool for evictable idle prefixes. Active reservations take priority. Zero disables idle prefix retention. |

Warm up the supported packed shapes on all ranks before reporting readiness. Log the resolved capacities, cadence, and shape limits at startup. Trace each plan's live sequences, kernel launches, and row and copy budgets so the admission and fairness gates can be checked directly.

Bound ingress by request count and retained bytes and carry that admission permit through release. Return HTTP `429` for a full ingress budget before starting SSE and `503` when admission is closed. Bound per-request token buffering and reserve terminal delivery capacity. Rank threads use nonblocking sends. A disconnected or persistently backpressured client triggers cancellation of that request, with an explicit error for an attached client on overflow. Selected finish reasons and resource release are idempotent. On shutdown mark readiness false, close admission, drain within the termination budget, then cancel and synchronize the remainder. ## Model execution

**Packed forward.** Add a batch descriptor alongside the existing single-sequence metadata ABI. Describe per-sequence row ranges, logical positions, valid context lengths, cache addresses or page tables, and sampling state. Map each packed row to its sequence and logical position. Run shared weight operations and TP communication over the packed rows. Attention, indexer, KV append, compression, Engram, and sampling must respect each sequence's boundaries. Segment-local kernels are valid for the first implementation where they sit inside a shared forward. Start with eager execution at two sequences, then exercise four and eight. Size kernels by packed rows. Two six-row DSpark verifications already exceed the eight-row limit of the incumbent low-row MoE and GEMV paths. Qualify a wider target forward with consistent sampling numerics before choosing production verify widths. [Decode kernel guards](../crates/engine/src/model.rs#L2449)

**Resumable CED prefill.** Split `Rank::prefill` into initialization, encoder chunks, and decoder replay. Compute the replay boundary from the final prompt length, then restore or reconstruct the retained encoder tail once. Each encoder chunk updates its KV source and tail and advances the request cursor. After the last chunk, run bounded decoder replay once and sample the first token. A resumed chunk must use its original sequence positions and causal boundary. For images, retain sequence-local image identity and isolate GPU staging; schedule only complete image spans where the vision path requires them. Qualify vision staging under load before enabling batching on image traffic. [Current CED implementation](../crates/engine/src/model.rs#L2304) · [vLLM's bounded replay for V4.1](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-10-07-deepseek-v41-flash.md)

**Sampling and DSpark.** Start with autoregressive decode to qualify position mapping, cache isolation, and sampling. Keep seed, RNG counter, and RNG purposes per request and independent of packed row order. Add fixed-width DSpark with per-request draft, verify, accept, and output state. Sweep autoregressive decode and draft widths 1, 3, and 5 at active batch sizes 8, 16, 32, and 64 where supported, across context buckets. Optimize for accepted output tokens per GPU-second at the streaming target. A 64-request, five-draft verification has up to 384 target rows. Profile wider packed GEMMs, MoE, segmented attention and indexer, communication, and distributed sampling before choosing shapes. Use bounded graph buckets keyed by compatible kernel shape and verification width. Use eager execution for unsupported shapes. Track accepted, rejected, and padding rows separately, mask padded writes, and make KV readable only through the verified causal boundary. Keep the incumbent adaptive graph available for the single-slot engine. Add adaptive packed widths if fixed widths leave material goodput on the table. [Current sampling state](../crates/engine/src/model.rs#L4047) · [vLLM graph dispatch](https://docs.vllm.ai/en/stable/design/cuda_graphs/)

**Commit and retire.** Track computed KV length separately from accepted tokens and from the engine output prefix after stop and length clipping. Prefill can emit a first token whose input KV has yet to be forwarded, and verification can write provisional rows beyond the accepted prefix. Truncate provisional writes and forward any missing final token before completion capture. Finalization uses the engine's existing output boundary and the HTTP adapters keep their existing text-stop and usage behavior. A cancelled request before the first sample publishes no completion image. GPU state remains leased through its last reader, including asynchronous snapshot capture. [Decode cache boundary](../crates/engine/src/decode_cache.rs#L3) · [Current completion path](../crates/server/src/engine.rs#L363)

## GPU cache and replica reuse

Allocate variable-length pages from a shared pool per rank. Compressed KV, index payloads and scale tiles, and Engram history grow with the prefix. Sliding-window KV and compressor histories wrap at the larger of the prefill chunk plus required lookback and the saved snapshot tail plus verifier slack. Preserve logical positions and serialize raw ring segments in their original logical order. Hot reuse compares tokens and image spans and checks that the retained raw tail covers encoder replay. Pool sizing includes slot-local encoder and draft tails and temporary work that persists across steps. [Cache layout](../crates/engine/src/batch_decode.rs) · [Snapshot layout](../crates/engine/src/kvstore.rs) · [vLLM hybrid KV manager](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)

Reserve the worst-case page footprint for the aligned prompt, admitted output cap, and existing 64-token lookahead allowance before admitting the request. Assign pages as positions are reached. Commit or release pages atomically across required regions, and expose both reserved and physically used capacity. Size the live pool from allocator regions, alignment, and retained state. Size the host snapshot pool and transfer staging separately from measured snapshot bytes and retention lifetimes. This gives admitted requests guaranteed space to finish. If full reservation still blocks the standard tier after output limits and tiering are applied, compare denser retained-state layouts and define bounded preemption and deterministic resume before offering smaller growth reservations. Prove progress at pool exhaustion, including snapshot or recompute, seed and verified-prefix preservation, and a cap on repeated preemption. [Existing output limits](../crates/server/src/generation.rs#L55) · [Current host memory budget](../crates/server/src/host_budget.rs#L39)

Keep Redis lookup and revalidation, RDMA fetch, publication waits, and onboarding on bounded background workers. Serialize same-session requests on each replica through retirement and the existing bounded publication and fencing handoff. Revalidate the candidate close to restore, keep the original job until alignment is confirmed, and apply alignment once with the existing capacity and image-span checks. Validate snapshot geometry on every rank and onboard a remote prefix after it restores successfully. A request may continue computing during onboarding. If the handoff expires without a valid publication fence, release the publication work. For stale or incompatible snapshots use the existing cold path. Preserve required-RDMA failure behavior. Count outstanding preparation and restore leases against the host memory budget and drop candidate leases promptly after use. [Current revalidation](../crates/server/src/engine.rs#L67) · [Onboarding](../crates/server/src/engine.rs#L269) · [Host budget](../crates/server/src/host_budget.rs#L39)

Gather and scatter the existing logical snapshot format. Prefix restore rebuilds transient decoder replay state locally. Use bounded copy quanta and CUDA events for restore and export so an unrelated decode can run between copies. Stage any mutable snapshot regions before resuming their writer, and retain immutable source pages until the copy completes. Host transfer and fenced publication can then finish independently. Preserve both prefill and completion publication when staging capacity allows. Give the new backend a distinct cache fingerprint until bidirectional restore and continuation with the incumbent qualify. ## Acceptance and benchmarks

- **Continuous admission.** Start A, submit B after A emits, and verify B emits before A finishes. A trace must show A and B in one shared target forward. Retire A and reuse its slot for C while B is still decoding. Verify a long prefill advances at the configured cadence under decode load, and that a request which only fits alone eventually runs.
- **Correctness.** Test per-request logits and token progression against an isolated run using the same backend and inputs. Require identical fixed-seed outputs across slot and order changes on the deterministic path. When comparing autoregressive to speculative backends, use teacher-forced logits, greedy checks, and sampling distribution checks because their RNG consumption differs. Cover 127/128/129-token boundaries, page and compression boundaries, near-1M input, prefix alignment and rewind, vision spans, accepted/rejected draft tails, stop and length, and slot reuse after cancellation. Exercise cold, local-hit, remote-hit, stale-owner, and mixed-version handoffs. Check SSE and JSON, including tools, usage, and terminal errors, on Chat Completions, Completions, Responses, and Messages.
- **Resource bounds.** Test queue overload, disconnects while queued and active, slow consumers, cancellation during in-flight restore and verify, and shutdown. Confirm bounded queues and stable HBM and host usage through a sustained churn test. Every cancelled or completed request returns its reservation, pages, slot, and candidate lease. Repeat with simultaneous retirement and same-session waiters.
- **Replica performance.** Compare the incumbent DSpark path with enabled batching on the same checkpoint, context limit, GPU profile, workload, cache state, and offered load. Run at least three warmed trials at concurrency 1, 2, 4, and 8, then raise offered load and resident limits through 16, 32, and 64 until the SLO or resource limit binds. Use the frozen workload with thinking and tools, a decode microbenchmark, long prefill against active streams, and the maximum valid input in the long-context pool. Report goodput, TTFT, inter-chunk gaps, per-request decode rate, errors, queue wait, resident and active occupancy, prefill progress, verification acceptance, and peak HBM and host memory. Publish the attainable occupancy and the binding constraint. [Incumbent single-request benchmark](../README.md#reproduce-the-demo)
- **Fleet performance.** Repeat at two or more groups and record observed scaling efficiency. Run the 500-session soak, the sustained 500-generator test, and the open-loop overload sweep. Exercise a synchronized start, mixed cache fingerprints, simultaneous tool returns, parallel branches, a near-1M request during standard load, Redis failover, the largest expected node or replica loss, and a rolling restart. Include cold and post-failure results and publish the per-cohort SLOs, error denominators, peak live sessions and actively generating streams, and normalized goodput per GPU. Verify zero cross-tenant or cross-branch cache reuse. When the available fleet misses a target, report its highest sustained passing session and stream counts, the limiting resource, and the measured cost of the next capacity step.

Keep **1.5× useful decode throughput at concurrency eight**, **90% of incumbent single-request decode and long-prefill throughput**, and **p95 single-request short-prompt TTFT within 15%** of incumbent as engine regression gates. The fleet claim requires the absolute coding workload targets. Record the workload, GPU count, software revision, pool budgets, and the breakdown of queueing, copy, and kernel time.

## Backend and topology decisions

Run the incumbent single-slot engine in a replicated fleet as the low-load control. Evaluate packed Ultrafast TP4/TP8 and vLLM TP and data-parallel attention with expert parallelism (DEP) on equal GPU budgets and the same manifest. Compare their minimum GPU count at the service targets, failure allowance, successful coding turns per GPU-hour, and performance at concurrency one. The upstream B200 AgentX recipe includes DEP8 runs at offered concurrency 512 through 576 on the 0909 launch checkpoint. It uses different kernels, cache budgets, and parallelism. Use it as a topology reference and qualify the serving checkpoint and target workload directly. [InferenceX B200 submission](https://github.com/SemiAnalysisAI/InferenceX/pull/4786) · [vLLM exact-model recipe](https://github.com/vllm-project/vllm/blob/main/recipes/models/deepseek-ai/DeepSeek-V4.1-Flash.yaml)

- **Use replicated packed TP** if it clears the service targets at an acceptable GPU count. Keep scaling independent groups while measured routing and cache overhead allow it.
- **Evaluate DEP early** if packed TP misses the throughput per GPU needed for the intended fleet, or profiles attribute the limit to expert work, duplicated weights, or TP collectives. Start with upstream DEP on supported hardware. Prototype a native DEP path only if the same-hardware comparison establishes a benefit worth the kernel and communication work.
- **Evaluate disaggregated prefill and decode** if bounded prefill and routing keep missing TTFT or stream-gap targets together. Use measured prefix bytes, transfer and replay times, and separate prefill/decode arrival rates to size the split. Current host session snapshots inform a handoff design. Live continuation needs its own page leases, freshness, activation fence, and failure recovery. Benchmark upstream P/D as the reference. Published rack-scale AgentX throughput includes cached input, uncached input, and output. Use output goodput measured by our harness for sizing. [vLLM GB300 disaggregation study](https://vllm.ai/blog/2026-10-23-deepseek-v41-flash-pd-wide-ep)
- **Use the backend that qualifies the workload.** If vLLM meets the workload at lower GPU count or Ultrafast misses the latency targets, use vLLM for standard coding traffic and consider a separate Ultrafast low-latency tier where measured. Validate both through the same gateway, with protocol parity and sticky compatibility cohorts. If no tested configuration passes 500 active streams, size and publish the strongest proven capacity separately from the 500-session result.
